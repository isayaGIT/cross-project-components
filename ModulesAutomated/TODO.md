Inspect source boundaries and contracts before implementation. Do not run tests/builds or commit/push unless explicitly requested.

Map the actual request/data flow and all consumers first; identify public entry points, response contracts, dependencies, and integration boundaries from source evidence. Preserve character identity/build context across consumers and avoid duplicated domain state. Deliver a reusable native Swift module with a README. ## Research and integration required

- [ ] **Realtime Voice Calling / AI Voice Conversation System** — This feature is not present as a complete subsystem in the original repository. Carefully research and adapt an existing GitHub implementation rather than inventing a call stack from scratch. Separate the native iOS call/media client from the backend agent/signaling/token/session services; select only the required pieces and preserve licenses/attribution. Investigate these starting points:
  - LiveKit Swift SDK (Apache-2.0; realtime audio/video/data SDK, supports self-hosted or cloud server): https://github.com/livekit/client-sdk-swift
  - LiveKit Swift AI voice-agent starter (MIT; iOS/macOS/visionOS client example): https://github.com/livekit-examples/agent-starter-swift
  - LiveKit Swift examples, including CallKit/PushKit integration: https://github.com/livekit-examples/swift-example-collection
  - SwiftCall (MIT; WebRTC + CallKit + PushKit + Socket.IO and reconnection/state-machine reference): https://github.com/xenophiliamee/SwiftCall
  - Baseline WebRTC iOS demo (explicitly not production-ready): https://github.com/stasel/WebRTC-iOS

  Initial assessment: if the goal is a live conversation with an AI character, evaluate LiveKit + LiveKit Agents first because the architecture is designed for realtime voice agents; if the goal is ordinary person-to-person VoIP, evaluate the WebRTC/CallKit/PushKit call flow instead. SwiftCall's README explicitly describes its signaling server as a minimal demo, so do not transplant that server as production infrastructure. Verify current repository code, maintenance, dependency versions, license, security, deployment model, latency/turn-taking, interruption handling, reconnect behavior, iOS background/incoming-call requirements, and integration with the existing character/LLM/TTS pipeline before choosing what to adapt. Keep the backend work backend-only; native call UI is outside this automation's scope.

## Additional important omissions found during `cloud/` source audit

These candidates were identified by reviewing the real backend service inventory, `cloud/server.py` call sites, and the existing `cloud/llm/` package. They are intentionally separate from the already-listed character-response, LLM-routing, TTS, diary, and voice-call work.

- [ ] **Memory Recall + Character Context Injection** — **Very high priority.** The server has a nontrivial memory pipeline around `_load_character_config`, `_load_recall_pool`, `_mem_tokenize`, `_mem_bm25`, `_mem_semantic`, `_mem_extract_entities`, `_mem_entity_boost`, `_mem_search`, `_build_recall_section`, and `_build_char_config_section` (`cloud/server.py`, around the memory/character-context section). It combines seed memories, runtime memories, and `memory-bank`, then injects recalled memories and character configuration into replies; comments indicate this context is also used by moments/comments. Extract this as a reusable backend context assembly + retrieval subsystem, preserving ranking, entity boosts, source labels, token/character budgets, and consumer-specific prompt contracts. Audit every consumer before implementation so different reply paths do not silently diverge. Do not conflate this with the Character Build → Response Propagation task: this task is specifically retrieval, ranking, and context injection.

- [ ] **LLM Gateway + Provider Transport + Streaming + Usage Telemetry** — **Very high priority.** The package has cohesive files `cloud/llm/gateway.py`, `providers.py`, `transport.py`, `stream.py`, `anthropic.py`, `cost.py`, and `telemetry.py`, beyond the already-listed routing module. Extract the reusable call execution layer: provider adapters, request/response normalization, streaming/chunk behavior, retries/error mapping where present, usage/cost accounting, and telemetry. Map dependencies and public call sites before choosing the exact module boundary; avoid duplicating `LLMRouting` or turning this into a single-file transport wrapper. Existing `LLMGateway`/`LLMTransport` outputs are historical fragments and should be audited against the whole package, not assumed complete.

- [ ] **Conversation Persistence + SaveStore Contracts** — **High priority.** Review `cloud/services/save/store.py`, `private.py`, `story.py`, `flags.py`, `types.py`, plus the chat save/load/delete/export/import handlers in `cloud/server.py`. Extract the shared persistence contract while keeping private-chat and story channels physically/logically isolated, SQLite schema migration behavior, incremental upserts, pagination/window reads, metadata patching, message edits/deletes, and import/export compatibility. This is foundational for a native app and must not merge channel-specific stores or invent a new on-disk format without a migration plan.

- [ ] **Moments / Social Feed Generation + Interaction Workflow** — **High priority.** The backend has a substantial cluster for moments generation, scheduled/catch-up generation, comments/replies, retries, user-created moments, image handling/thumbnails, user-comment understanding, and index rebuilding. Trace the workflow across `cloud/server.py` and the relevant helpers/services (`cloud/services/moment_thumbs.py`, LLM routing, memory/context injection, schedule logic). Extract a cohesive domain workflow rather than migrating the many endpoint handlers one-by-one. Preserve idempotency, pending-comment recovery, IDs, storage contracts, generation status, and the differences between generated and user-authored content.

- [ ] **Proactive Character Lifecycle / Sleep-Wake / Schedule Orchestration** — **High priority.** `cloud/server.py` contains background heartbeats and transitions such as `_sleep_tick`, `_on_pre_sleep`, `_on_wake`, private-moment triggers, diary/mailbox scheduled generation, and catch-up planning; `cloud/services/schedule.py` owns character schedule logic. Extract time-zone-aware state transitions, trigger conditions, persisted session state, missed-run/catch-up handling, and event contracts. This is a backend character-lifecycle system, not merely a timer utility. Keep schedule generation and individual diary/mailbox domain logic as separate dependencies where appropriate.

- [ ] **Authentication + API Security Boundary** — **Important foundational work.** Review the passkey/authentication handlers, rate limiting, token checks, path/media validation, and outbound URL safety helpers in `cloud/server.py` (including `_auth_rate_allowed`, `_safe_chat_id`, `_is_blocked_static_path`, `_is_safe_outbound_url`, and media path resolution). Identify the actual trust boundary and reusable policies needed by the native app/backend. Preserve fail-closed behavior and server-side secret handling. Treat this as a security-sensitive audit/extraction; do not weaken controls or move credentials into the client.
